# 01 構成

API サーバー(`api/`)のディレクトリ構成と、各層の役割をまとめる。

## 全体像

LLM を使った回答サービス。回答の方式ごとに `apps/` 配下へ 1 つのアプリとして実装し、アプリ間で共通する処理は `libs/` に置く。

```
api/
├── interfaces/   FastAPI の入口(認証・接続・送受信だけの薄い層)
│   ├── main.py         アプリケーションの生成
│   ├── urls.py         ルーターの登録
│   ├── middleware.py
│   ├── routers/        エンドポイント(1 アプリ = 1 ファイル。アプリ以外の API も 1 機能 = 1 ファイル)
│   └── dependencies/   認証などの FastAPI 依存関係
├── apps/         回答アプリ(1 アプリ = 1 ディレクトリ)
│   └── <app_name>/
├── libs/         アプリ共通の処理
│   ├── database.py     DB 接続
│   ├── models/         ORM モデル(全テーブル)
│   ├── repositories/   DB アクセス
│   ├── agents/         LLM エージェント(プロンプト + LLM 呼び出しの組み立て)
│   ├── prompts/        prompt_templates.yaml の読み込み
│   ├── external/       外部サービスのクライアント(LLM など)
│   ├── websocket/      WebSocket への送信
│   └── tasks/          バックグラウンドタスク
├── admin/        管理画面(sqladmin)
├── config/       環境変数の読み込み
├── db/           alembic マイグレーション
└── scripts/      手動で実行する補助スクリプト
```

## 依存の向き

```
interfaces → admin → apps → libs → config
```

- 左の層は右の層を使う。逆向き(`libs` から `apps` など)は禁止
- `interfaces/main.py` が `admin/` を組み込む(`init_admin`)。`admin/` から `interfaces/` は使わない
- 間の層は飛ばして使ってよい(例: `interfaces` が `libs/repositories` や `config` を直接使う、`admin` が `apps` を通さず `libs` を使う)

## interfaces/

クライアントとの通信だけを担当する。

- 担当すること: 認証、WebSocket の接続・受信・送信・切断、エラー時の応答
  - 現状、認証は HTTP(`dependencies/http.py`)だけ。WebSocket の認証は未実装で、後日 `dependencies/websocket.py` に追加する予定
- 担当しないこと: 回答の生成と送信。受け取った入力と WebSocket をアプリの controller に渡すだけにする(回答と `stop` はノード、`done` は controller が送る)
- クライアントからの送信は 1 接続につき 1 回
- 接続を閉じるのはクライアントの責務(`done` を受け取ったら閉じる)。サーバーからは、`WS_TIMEOUT_SECONDS` を過ぎたとき(とエラー時)だけ閉じる

### 送信の形式

| 送信 | 形式 | 送る層 | 意味 |
|---|---|---|---|
| 回答 | `{"message": {"agent", "content", "content_key", "stop", "cancel"}}` | nodes | 回答の一部。ストリーミングで続けて送る |
| 回答の終わり | `{"message": {..., "stop": true}}` | nodes | 1 つの回答が終わった。回答が複数あるときは、回答ごとに送る |
| 処理の終わり | `{"done": true}` | controller | この接続での処理がすべて終わった。クライアントは受け取ったら接続を閉じる |

クライアントは `stop` で 1 つの回答の表示を確定し、`done` で接続を閉じる。`done` が来ないまま切断されたら異常として扱う。

## apps/

回答の方式ごとに 1 ディレクトリを作る。どのアプリも次の構成に揃える。

```
apps/<app_name>/
├── <app_name>_controller.py   入口。router から呼ばれ、AI ロジックを制御する
├── flows/                     処理の流れ(グラフの組み立て)
│   └── flow_data.py           ノード間で受け渡す FlowData
├── nodes/                     個々の処理ステップ
└── prompt_templates.yaml      そのアプリ専用のプロンプト(flow → node → agent の階層)
```

### <app_name>_controller.py

router とアプリの境目。全アプリで同じ形の関数を公開し、router からは同じ呼び方ができるようにする。

```python
async def run_<app_name>(ws, chat_session: ChatSession, text: str) -> str: ...
```

- 関数名はアプリごとに `run_<app_name>` とし、router で import したときに名前が衝突しないようにする
- `ws` はノードまで渡し、ノードが回答を送る。`ws` に `None` を渡すと送信せずに回答だけを返す(テスト・評価・バッチ用)
- 引数は必要に応じて追加してよい。追加するときは全アプリで揃える

controller は flow の中身を知らず、flow の入口と出口だけを使う。flow を修正しても controller は修正しない。

- 入口: `arun(prompt)`(ユーザーのテキスト)
- 出口: `FlowData.content`(最終的な回答)

controller が担当すること:

- 入力を受け取り、flow を実行し、最終的な回答を返す
- flow が終わったら `done` を送る(`libs/websocket/sender.py` の `send_done`)。flow は `arun` の中で保存まで終えているので、`done` の時点で保存は済んでいる
- flow が終わった後の処理(ログなど)。クライアントを待たせず、接続のタイムアウトでキャンセルもされないよう、`run_in_background`(`libs/tasks/background_task.py`)で切り離して実行する
  - `done` より先に登録する。`done` の送信に失敗(クライアントが先に切断)しても、flow が成功していれば後処理は行う
  - flow が例外で終わったときは後処理を行わない(`FlowData` がないため)
  - 後処理の例外は `run_in_background` がログに出す。クライアントには返さない
  - 実行中の後処理は、サーバーの終了時に `BACKGROUND_TASK_SHUTDOWN_TIMEOUT_SECONDS` まで待つ

controller が担当しないこと:

- WebSocket の接続・受信・切断(`interfaces/routers` の担当)。回答と `stop` の送信(`nodes/` の担当)
- 処理に必要なデータの準備(会話履歴の取得など)。どのデータが必要かは flow・ノードごとに違うため、必要とするノードが取得する
- プロンプトの組み立てや LLM 呼び出しの細部(`flows/`・`nodes/` の担当)
- 結果の保存(`flows/` の担当)

### flows/ と nodes/

- `flows/`: LangGraph のグラフ(State・ノードのつなぎ方)を組み立て、`arun(prompt)` で実行する。LangGraph に依存するのは flow だけにする
  - ノード間で受け渡すデータ(入力・回答など)は flow の `FlowData` に持つ。LangGraph の State は通ったノードの記録(`history`)だけにする
  - `FlowData` は `flows/flow_data.py` に置く。flow とノードの両方がそこを import し、ノードが flow のモジュールに依存しないようにする
- `nodes/`: 1 ステップの処理。State には依存せず、flow の `FlowData` を受け取り、その内容に従って処理し、結果を `FlowData` に書き込む
  - ノードは `FlowData` の内容で動きが変わるため、flow の `__init__` ではなく、グラフの各ステップの中で生成する
- ノードは回答を `libs/websocket/sender.py` の `ContentStreamSender` などで `ws` に送る(ノードに基底クラスはない)。回答は `stop: true` を送るまで続く(`stop: true` が 1 つの回答の終わりの合図。形式は「送信の形式」を参照)
  - 2 つ目の回答を送るかどうかは flow が決める(グラフの分岐)。回答を送るノードは、それぞれ自分の回答の終わりに `stop` を送る
- 保存は flow が `arun` の最後(`finally`)に `FlowData` をもとに行う。ノードは保存せず、結果を `FlowData` に書き込むだけにする
  - 分岐・分岐の理由・RAG のコンテキストなど、保存する内容がそろうのは flow が終わった時点のため
  - flow がすべて終わってから保存するので、途中のノードが読む会話履歴に今回の分が混ざらない
  - 回答は `ContentStreamSender.content` に受け取るたびに溜まる。ノードは `send()` を `try/finally` で囲み、`finally` で `FlowData.content` に移す。途中で切断されても、そこまでを保存できる
  - `libs/repositories` はアプリごとの `FlowData` を知らない。`FlowData` から repository の引数への置き換えは flow が行う

> MVC の「controller」(HTTP を受ける層)とは意味が異なる。HTTP / WebSocket を受けるのは `interfaces/routers` で、ここでの controller は AI ロジックの制御役。

### 呼び出しの流れ

```
クライアント
  ⇅ WebSocket
interfaces/routers/<app_name>.py           認証・接続・受信
  ↓ run_<app_name>(ws, chat_session, text)
apps/<app_name>/<app_name>_controller.py   AI ロジックの制御・done の送信・後処理
  ↓
apps/<app_name>/flows/, nodes/             AI ロジック本体・回答の送信(nodes)と保存(flows)
  ↓
libs/                              DB・LLM クライアントなど
```

## libs/

複数のアプリ、または `interfaces/`・`admin/` から使う共通処理を置く。関心ごとにサブディレクトリを分ける。

- `models/`: ORM モデルはすべてここに置く。alembic は `libs.models` の `Base` からマイグレーションを生成する
- `repositories/`: DB アクセス。ファイル名は `<model>_repository.py`(例: `chat_session_repository.py`)
  - DB セッションは引数で渡さず、各関数の中で `async with AsyncSessionLocal() as db:` で開く。呼び出し側は `get_history(chat_session)` のように `db` なしで呼ぶ
  - DB アクセスはすべて repository を通す。`interfaces/`・`admin/`・`apps/` でクエリ(`select` など)を直接書かない
  - 例外: `prompt_template_repository.py` は同期のセッション(`db_session`)を使う。`SAVE_PROMPT_TEMPLATE` が有効なとき(ローカル開発用。本番では有効にしない)だけ呼ばれるため、イベントループを止めても問題ない。意図的なので修正・指摘は不要
- `prompts/`: 各アプリの `prompt_templates.yaml` の読み込み(`set_store`)と取得(`get_prompt_template`)。DB への保存は `prompt_template_repository.py` に任せる
  - 全アプリの YAML を 1 つの store にまとめるため、`flow_name` が重なると `set_store` がエラーにする
- `agents/`: LLM エージェント。システムメッセージ・会話履歴・入力からチェーンを組み立てる
  - 会話履歴は agent が取得せず、ノードが取得して `history=` で渡す(どの履歴をどう渡すかはノードごとに違うため)
  - `chat_session` はトレース用の metadata(`session_id`・`trace_user_id`)にだけ使う
- `external/`: LLM など外部サービスのクライアント
- `websocket/`: WebSocket への送信。「送信の形式」の組み立てはすべて `sender.py` に置く(`ws` が `None` のときは送らない)
- `tasks/`: バックグラウンドタスク(後処理の切り離し)

## admin/

sqladmin による管理画面。ユーザー向けの機能ではないため、`interfaces/` とは分けている。

## db/

alembic の設定とマイグレーション。マイグレーションは `make migrations msg=xxx` で自動生成する。
